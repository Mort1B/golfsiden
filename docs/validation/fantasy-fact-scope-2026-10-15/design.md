Declared before comparative measurements. Baseline is application source at
`e3ee966`; candidate changes only owner selection before canonical bulk facts.

- Build the pinned baseline from an owned temporary `git archive e3ee966` and
  rebuild the candidate with the same locked debug profile; retain source/binary
  build provenance. Use owned disposable PostgreSQL 17 Alpine,
  loopback-published API in its network namespace, Vite and real Chrome.
- Populate one/five-round tournaments through existing APIs: eight zero-handicap
  golfers, four scramble teams per round, 18 par-four holes, two managers with
  different first-round picks. Open, score, confirm and complete every round.
  No batch/save-refresh benchmark, schema/index, dependency or hosted change.
- Keep both binaries on the same fixture identities and facts. Snapshot the owned
  database before the first Fantasy result materializes locks; restore it before
  candidate first-read comparison, with the API stopped. Retain no dump in Git.
  Require exact in-memory JSON equality for first and steady round results,
  overall results and all golfer/manager breakdowns. Publish only scalar parity
  and normalized metrics, never bodies, credentials, sessions or real identities.
- First populated reads are separately timed and must each finalize all 1/5
  windows, 2/10 manager selections and 0/8 carries. Subsequent reads must not
  change those counts. No cold-disk claim: setup already touched database pages.
- Run baseline/candidate/candidate/baseline blocks per fixture. Each block has
  tracking none then top, five warmups after reload/restart and ten measured
  sequential complete scoped HTTP reads per mode (20 per build/mode/fixture).
  Set tracking globally and prove empty none snapshots and positive top counts.
- Require 25 tracked statements per scoped read, including 21 SELECT/WITH calls;
  keep lock rows equal to tournament round count. Baseline canonical owner rows
  are 4/20; candidate must return exactly 4 at both sizes. This owner budget would
  fail the five-round baseline. Overall and golfer/manager breakdown controls
  must retain 4/20 owners for both builds. Canonical fact SQL/content is unchanged.
- Report HTTP median/nearest-rank P95 and SQL aggregate execution/call/row/buffer
  counts separately. No subtraction to infer Rust CPU or zero observer overhead.
  Compare both tracking modes and the one-round no-extra-round control; retain
  raw samples and order. No load, concurrency or production speedup claim.
- Preserve existing sibling-lock/revocation, invalid/foreign target rollback,
  lazy cross-round finalization, carry-forward, canonical fingerprint and hidden
  result regressions. Add final-expiry rollback after a canonical fact-table wait
  and cross-surface parity in existing six-format/hidden/carry fixtures.
- Run focused tests and complete affected Rust/PostgreSQL ladders, migrations and
  seed. Measure only after these CPU/database jobs stop. Then check candidate
  settled boards in Chrome at 320/1280, console/network errors and isolated
  anonymous read denial.
  Frontend source/contracts stay unchanged; no frontend unit/lint ladder needed.
- Independent read-only source and evidence review, current docs and scope checks
  precede main publication. Reject the runtime change if parity/authority gates
